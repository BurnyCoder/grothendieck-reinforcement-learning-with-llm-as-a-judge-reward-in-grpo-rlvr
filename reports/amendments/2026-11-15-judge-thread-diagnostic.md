# Development diagnostic for judge decoding latency

Date: 2026-11-15. No comparative evaluation or locked audit exists.

The registered Gemma CUDA runtime loaded successfully. Its first v3 development
request processed the prompt but then decoded unusually slowly. Stopping the
concurrent Qwen judge did not resolve the observed slowdown. A native stack
sample found the CPU workers in OpenMP barriers around matrix operations.
This is a diagnostic observation, not proof of a cause. The partial response,
server log and stack sample are preserved under `reports/development/`.
Calibration was interrupted without assigning a score to that partial response.

Before changing the serving configuration, run the pinned upstream
[`llama-bench`](https://github.com/ggml-org/llama.cpp/tree/b1b770d90d94cad9e9ea5b993bdbc383a522fb28/tools/llama-bench)
with CPU thread counts **1, 4, 8**, in that order, with two repetitions each.
Use a synthetic prefix of 2048 tokens and measure 16 subsequent decoding steps.
The benchmark's depth setup occurs before its measured generation interval;
its allocated context is prefix plus generated length, not the server's maximum
context. Keep the registered model, quantization, GPU offload, batch size,
microbatch and F16 KV types. Stop other project model processes first. Preserve
standard output, standard error, command, environment wait settings and partial
results. Stop the entire diagnostic after 900 seconds if unfinished.

Prefer the fastest completed thread setting for a subsequent end-to-end
development check. Publish any chosen serving change before recalibration;
changed runtime identities invalidate previous calibration passes. A synthetic
speed improvement cannot establish correct structured judgments or mathematical
quality. If every candidate remains slow, retain that result and investigate
the next cause explicitly rather than calling a partial calibration a pass.

Related upstream reports motivate measuring synchronization costs, but use
different hardware and do not establish our diagnosis:
[OpenMP barrier overhead](https://github.com/ggml-org/llama.cpp/issues/31516),
[threadpool sharing issue](https://github.com/ggml-org/llama.cpp/issues/9588).
The first report concerns Intel hybrid CPUs; this host uses an AMD CPU.

Command: `bash scripts/run.sh benchmark-judge`. No problem answers or reward
scores are generated by this diagnostic. The mathematical protocol and preferred
Qwen3.5 policy remain unchanged.
